# Social 互動通知:評估與分期(IA 重整 Phase 5)

2026-09-07。對應 `docs/IA-PLAN.md` D6 決議:自媒體 Social 頁評估串接「發文分享留言的通知功能」,連動互動式發文與留言——**先評估、維護者拍板、再動工**。

## 1. 目標

創作者需要及時知道「誰在我的內容下留言/提及/追蹤」,以便回覆互動(互動率影響演算法觸及);理想終點是在 App 內直接回覆,起點是「看得到」。

## 2. 各平台現況評估(2026-09-07 查證)

| 平台 | 通知取得方式 | 即時性 | 前置門檻 | 觸及本專案紅線? |
| --- | --- | --- | --- | --- |
| **Threads** | Graph API 輪詢(回覆清單、媒體互動數據 insights) | 分鐘級(**無 webhook 推送**) | token 已由 worker 代管(現成) | **是**——worker 目前紅線「只接收貼文內容與 token」,代讀互動資料屬職責擴張,需修訂措辭 |
| **Instagram** | Graph webhook(留言/提及事件推送) | 即時 | **商業帳號**+綁粉專+App Review | 同上;且 IG 為後續平台增量,尚未開工 |
| **X(Twitter)** | mentions timeline API | 輪詢 | **付費層**(基本存取已不夠) | 同上;量計費,報酬率存疑 |
| **YouTube** | PubSubHubbub push(頻道活動)、Comments API | 近即時 | 現有 Google OAuth 可擴 scope | 留言 API 配額重;稽核前鎖私人政策增加變數 |
| **LINE** | 無個人動態 API | — | — | 永遠手動(既有決議) |
| **Gmail 通知信** | **既有唯讀 Gmail 串接**+規則分類 | 取決於各平台通知設定(通常即時~小時級) | **零**(已上線的能力) | **否**——純唯讀,emails 不落地,零新增權限 |

**結論:Gmail 通知信分類是唯一「零平台審核、零紅線風險、零新依賴」的路徑**,作為一期;直接 API 輪詢/Webhook 屬二期以上,需逐一拍板。

## 3. 一期(已實作,2026-09-07)

**做法**:Gmail 郵件新增分類「**互動通知**」——各平台寄到信箱的留言/提及/追蹤通知信,以規則式分類器識別(平台官方網域強訊號+具體互動片語,刻意不用「留言」等單詞避免誤傷讀者來信)。

- `classify.ts`:新增 `TAG_KEYWORDS['互動通知']` 與 `PLATFORM_NOTIFY_DOMAINS`(facebookmail/instagram/threads.net/youtube/linkedin,+3 分);互動通知一律不建議可發文(同活動通知定位)
- 郵件匣:篩選 chip 增「互動通知」;示範資料加一封 Threads 留言通知信
- 自媒體頁:新增「📬 最新互動」卡(最近 5 封互動通知信;真實信件可「查看信件」以 Gmail 搜尋開啟;未連線顯示示範資料)
- 紅線狀態:**完全不觸碰**——Gmail 維持 `gmail.readonly`、emails 不落地、回覆一律導回平台 App(誠實定位:看得到,不代回)

**限制(誠實清單)**:通知信取決於使用者在各平台的通知設定(未開 email 通知的平台看不到);分類為規則式,漏判/誤判可能;信件到達有延遲;不提供 App 內回覆。

## 4. 二期以上候選(需維護者拍板才動工)

- **方案 A——Threads 輪詢(建議下一步)**:worker cron 每分鐘順手拉取各 installId 的未讀回覆(insights/replies API),`/api/threads/interactions` 回傳給前端顯示。**前提**:修訂 `CLAUDE.md`/`BACKEND.md` 後端資料邊界紅線為「worker 得以代管之 token 呼叫該平台**唯讀** API 取得互動資料,回傳不落地儲存」;工作量約 worker 一個端點+前端一張卡,風險低(token 已在)。
- **方案 B——IG webhook**:即時最好,但商業帳號+審核+IG 代發本身尚未開工,建議與 IG 代發增量一併評估。
- **方案 C——X**:付費層,報酬率存疑,除非使用者實際有 X 互動需求。
- **方案 D——YouTube**:PubSub push 免費但留言 API 配額重,且稽核變數,觀望。
