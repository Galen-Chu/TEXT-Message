# 文管庫(文案管理)功能深化 — 規劃設計(LIBRARY-PLAN)

> 狀態:規劃設計稿(2026-09-02),待維護者確認範圍後動工。
> 背景:社群管理開發於 2026-09-02 收尾歸檔(見 `HANDOFF.md` 決策記錄 §5),本工作流提前為現行優先。

## 0. 目標與設計原則

把文管庫從「被動存放文字的地方」升級為「會累積複用價值的文案資產庫」:**發過的內容變範本、範本越用越順手、AI 幫你變出各平台版本**。

設計原則(不可違反):

1. **全純前端**——不動後端、不動 `worker/`,未設定任何環境的建置行為不變(CI 紅線)
2. **AI 全 BYOK**——沿用 `services/gemini/rewrite.ts` 的分流模式:無 key 明確提示、不動作、不失敗
3. **資料向後相容**——新欄位一律 optional,lazy 演進(舊 localStorage 資料直接可用,不做一次性 migration);持久化 key 維持 `text-message:v2`
4. **零新依賴**——不引入圖表/表單/狀態庫;趨勢圖以既有 design tokens 手寫 CSS 呈現

## 1. 現況盤點

| 項目 | 現況 | 缺口 |
| --- | --- | --- |
| 範本資料 | `Template {id, category, title, text}`,兩資料集(訊息管理/文案管理),持久化 | 無變數填值、無平台變體、無使用統計、單一分類維度 |
| 佔位符 | 範本 `c3` 以 `{{品牌名稱}}` 慣例使用 | 無偵測、無填值流程——套用到草稿後需手動改 |
| 發文記錄 | `publishedHistory`(platform/title/content/date/time)已真實化 | 與範本無連結;無法「一鍵把發過的存成範本」 |
| 統計 | Dashboard 僅「本月已發佈」一個數字 | 無頻率/時段/平台趨勢 |
| AI | 語氣改寫/郵件摘要/自訂指令 | 無平台適配變體生成、無 hashtag 建議 |

## 2. 功能設計(四期,每期獨立可交付)

### 第一期:範本填值與記錄連結(**2026-09-02 完成**)

**F1 佔位符填值流程**
- 偵測:`extractVariables(text)` 純函式,正則 `/\{\{([^{}:\s]+)\}\}/g`,重複變數只列一次、保持出現順序
- 觸發點:「套用到草稿」與「複製」時若含變數 → 開**填值 modal**:每個變數一個輸入欄(預設空),下方即時預覽替換結果;「略過」按鈕直接用原文
- 替換:`applyVariables(text, values)` 純函式;未填的變數保留原樣(`{{品牌名稱}}` 不消失,方便事後補)
- 持久化:預設值**不**跨範本記憶(第一期從簡;記憶機制列為決策點 D2)

**F2 以發文記錄建立範本**
- Social 頁每筆記錄加「📥 存為範本」動作 → 小 modal:標題(預設記錄標題)、分類(下拉,限「文案管理」的分類集)→ 寫入 `copyTemplates`
- 新記錄與示範資料皆可存(示範資料存出的範本會成為使用者真實資料,合理)

**F3 範本使用統計**
- `Template` 加 `appliedCount?: number`、`lastAppliedAt?: string`(ISO)
- 「套用到草稿」「複製」成功時計數(含填值後的套用)
- 文管庫卡片顯示「已用 N 次 · 最近 M/D」;分類清單頂部加排序切換(預設/最常用/最近使用)

第一期驗收:含 `{{變數}}` 的範本套用時出現填值 modal;發文記錄可存成文案範本並出現在文管庫;統計在重新整理後仍存在。

### 第二期:平台變體(**2026-09-02 完成**)

**F4 `platformVariants?: Partial<Record<PlatformKey, string>>`**
- 編輯/新增 modal 加「平台版本(選填)」區:依平台列出的 textarea,留空 = 使用通用內容
- 套用到草稿時:若草稿已勾選平台且範本有對應變體 → 插入變體版(多平台勾選且有多個變體時,依勾選平台逐一附加對應版本,各段前綴 `[Threads 版]` 之類的標示——詳細格式為決策點 D3);無變體 → 現行行為(通用 text)
- 複製時:預設複製通用版;卡片選單可選平台版(從簡:modal 下拉)
- 預覽卡邏輯不動(仍以 `draftText` 為準)

### 第三期:發文趨勢分析

**F5 趨勢區(Social 頁頂部或 Dashboard;決策點 D4)**
- 顯示門檻:`publishedHistory.length >= 5`,否則顯示「累積發文記錄中(N/5)」——**示範資料永不參與趨勢**(誠實紅線)
- 指標(全部 `utils/trends.ts` 純函式,配單元測試):
  - 近 30/90 天各平台發文數(堆疊/分組橫條)
  - 發文時段分佈(0–6/6–12/12–18/18–24 四桶)
  - 平台組合比例(單平台 vs 多平台同發)
  - 連續發文天數(streak)與最長紀錄
- 視覺:純 CSS 長條(design tokens、支援深色模式);無圖表庫

### 第四期:Gemini 產出輔助(BYOK)

**F6 平台適配變體生成**
- 草稿頁新增按鈕「✨ 產生平台版本」:以 `draftText` + 已勾選平台(各平台上限)呼叫新純函式 `generatePlatformVariants`(模型降級迴圈沿用 `rewrite.ts` 既有機制)
- 產出以可編輯清單呈現(每平台一欄,可改),兩個去路:「附加到草稿」(依平台變體格式插入)、「存為範本變體」(若有進行中來源範本則寫入其 `platformVariants`;無則另開存範本 modal)
- 無 key:明確提示不動作(同自訂指令模式);失敗:草稿不動、僅 toast

**F7 hashtag/關鍵字建議**
- 草稿頁「#️⃣ 建議標籤」:生成 3–5 個(附平台慣例,如 IG 慣用),點擊即附加到草稿尾端
- 同 BYOK 分流;無 key 不顯示按鈕或僅提示(擇一,決策點 D5)

**F8(遠期,本期不動工)**:以自身歷史貼文 few-shot 生成同風格新文案;Gemini grounding(`google_search`)查即時趨勢產主題靈感——需先驗證 key 方案的計費與可用性,屆時另立評估。

## 3. 資料模型演進(全部向後相容)

```ts
interface Template {
  id: string;
  category: string;
  title: string;
  text: string;
  // ── 以下新增,皆 optional ──
  appliedCount?: number;                              // F3
  lastAppliedAt?: string;                             // F3(ISO)
  platformVariants?: Partial<Record<PlatformKey, string>>; // F4
}
```

- `loadPersisted` 讀入後逐一補預設值(缺欄位 = 未啟用),不需 schema 版本號
- 排序狀態不落地(工作階段狀態)

## 4. UI 變動範圍彙總

| 頁面 | 變動 |
| --- | --- |
| 文管庫 Library | 卡片(使用統計)、modal(平台變體區)、排序切換、「存為範本」資料流入 |

## 5. 測試計畫

- 純函式(必測):`extractVariables`/`applyVariables`(重複變數、未填保留、特殊字元)、變體插入格式、`utils/trends.ts` 各指標(邊界:空記錄、同日多筆、跨月)
- Gemini 新入口:prompt 組裝/回應解析/錯誤碼對應(比照 `rewrite.test.ts`)
- hooks(`useAppStore`):計數持久化、存為範本寫入、變體套用分流
- E2E 維持 smoke 等級,僅在必要時補一條「填值後套用」的關鍵路徑,不擴大自動化範圍

## 6. 決策點(2026-09-02 維護者已確認)

| # | 問題 | 決議 |
| --- | --- | --- |
| D1 | 第一期範圍 | **F1+F2+F3 全做**(2026-09-02 完成) |
| D2 | 填值預設值記憶 | **不記憶**(理由非效能——localStorage 成本可忽略;主因是記住的值會過期,預填時若未察覺,過時的品牌名/折扣碼直接進貼文,對文案是實質風險;另避免多一組要清理的持久化資料。日後若重填真的頻繁,可作小增量補上) |
| D3 | 多平台變體插入草稿的格式 | **各段加 `[平台名]` 前綴**(第二期實作) |
| D4 | 趨勢區位置 | **兩頁都做**:Social 頁完整趨勢區 + Dashboard 精簡版(如連續天數與近 30 天平台計數)——趨勢為純函式,同結果兩處呈現近乎零成本(第三期實作) |
| D5 | 無 key 時 AI 按鈕 | **顯示但點擊提示**(與自訂指令一致;第四期實作) |
| D6 | Social 頁是否併入 Dashboard(2026-09-02 維護者提問) | **建議維持拆分,待確認**:兩頁資訊架構角色不同——Dashboard 是「摘要視角」(統計卡、近期排程、精簡趨勢),Social 是「完整資料域」(無限成長的歷史清單 + 篩選 + 完整趨勢 + 未來階段三恢復時真實平台 API 的落點);合併會使 Dashboard 過載、歷史清單塞不進總覽版面。拆分確實也利於未來擴充模組,但主因是角色分工 |
